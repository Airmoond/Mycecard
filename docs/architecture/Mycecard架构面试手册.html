00 / Start with the system

把一款卡牌游戏，
讲成清楚的工程。

从一局冒险到一次出牌，理解 Mycecard 的状态归属、规则边界和页面生命周期。面试时不背类名，讲清楚：为什么这样拆，解决了什么问题，又付出了什么代价。

从架构总览开始 ↓v0.6.1 · 本地单局冒险单文件 · 离线可用 · 支持打印

一句话抓住项目

Mycecard 是一个 Godot 回合制卡牌构筑游戏。工程以领域组织代码，分离静态内容、整局规则、单场战斗、页面编排和视听表现。核心规则不依赖场景树，因此游戏界面与数值实验可以调用同一套战斗实现。

玩家意图→流程 / 控制器→Session 裁决→State 改变→视图与表现消费结果
WHAT / 产品闭环

开局构筑 → 选藏品 → 三路择一 → 两战斗 + 一不期而遇 → 最终 Boss → 结算。普通战斗胜利后，三选一卡牌，也可跳过。

WHY / 重构主线

把“按按钮、算数值、切页面、播声音”从同一处拆开。新卡牌尽量配资源，旧页面不能重复提交，动画快慢不能改变伤害。

HOW / 学习顺序

先读 01–04 理解主干，再读 05–08 理解边界；最后用 09 的讲述练习和 10 的情境题验证自己能否解释原因。

先认清三个“结构”

目录结构回答“文件在哪”；运行时对象关系回答“谁持有谁”；调用链回答“事情怎么发生”。三者有关联，但不能拿文件夹名称代替架构解释。

01

Responsibilities & dependencies

五层职责，两个规则中心

整局由 RunSession 管，单场由 BattleSession 管。外层负责把输入交进去，把结果展示出来；规则层不反向操作按钮、场景、动画或音频。

↑ 上层读取 / 调用下层；结果经返回值和信号传出

把关键对象接起来：谁调用谁？

战斗页同样由 Router 创建；图中把它的控制器、模型和表现展开。线表示主要协作，不是完整引用清单，也不表示线程。

依赖方向的关键，不是“禁止所有互相通信”

允许：外层适配内层

BattleController 调用 session.play_card(card)；BattleSession 发出实际数值事件；控制器把事件交给 BattlePresentation。规则不必知道有没有画面，界面也不必重新算一遍伤害。

避免：界面成为第二套规则

不能只在按钮上检查费用，然后直接修改敌人生命。规则入口仍要检查阶段、手牌身份和费用，数值实验或其他调用者才能得到同样的约束。

面试表达

“这是按领域组织的分层架构，吸收了 MVC 的职责分离思路，但没有强行套一个完整框架。模型是场景无关的 Godot 对象，而不是完全脱离引擎的纯语言库。”

依据：run_session.gdbattle_session.gdbattle_controller.gd

场景树不是全部数据的家

画面由 Node 管，规则对象用 RefCounted。区分“应用活多久、这局活多久、这场活多久”，才能理解为什么切页不丢牌组，也不会把上场战斗的格挡带进下一场。

Definition 与 Instance：同名不等于同一张

STATIC / RESOURCE

CardDefinition：牌的种类

例如“打击”的 ID、基础费用、原画与效果列表。牌组可以重复引用同一个定义。运行时按只读契约使用，不把临时减费写回这里。

RUNTIME / REFCOUNTED

CardInstance：本场的一张牌

A 与 B 有不同实例身份，可以有不同临时费用。手牌区用实例身份识别控件，不能用 card_id 做唯一键，否则两张同名牌会互相覆盖。

武器实例由卡牌实例单向持有，记录当前攻击力与耐久；避免互相强引用形成 RefCounted 环。下一场战斗会重新创建卡牌和武器实例。

关于“只读”的准确说法

部分候选数组与结果字典调用了 make_read_only()，但 Resource 本身没有被深度冻结；只读容器里的对象引用也不是自动不可变。RunState 仍有公开可变字段，生产流程通过 Session 写入是架构约定。

03

Run state machine

一局冒险，由状态而不是页面推动

页面是状态的投影。先让规则接受一个命令，进入新阶段，再由 GameFlowController 展示对应页面。页面加载失败，不代表业务操作应该重做一次。

主菜单创建新会话
开局构筑传说 → 史诗 → 稀有
起点 / 藏品三选一
选定路线2 战斗 + 1 不期而遇
最终 Boss三种之一
胜败结算返回菜单结束本局

RunSession：命令与提交边界

生产流程通过 enter_node、choose_reward、resolve_unexpected 等入口操作本局。Session 检查阶段、候选、来源步骤等条件，并在成功时递增 step_token，保存只读命令结果。

它还负责把带身份的战斗结果接回冒险：校验战斗和节点 ID、生命范围与胜负一致性，拒绝已处理结果，然后进入奖励或终局。

RunState：事实与基础转移

保存当前阶段、地图解锁、选定路线、牌组、生命、藏品、事件候选与结果。它并非一个空数据袋：地图验证、基础状态转移、不期而遇实际应用等仍在这里。

这也是当前的演进点：RunState 已较大，可按地图绑定、事件状态等内聚职责继续拆，但不能让视图接走业务。

  • 不期而遇独立随机：三路各抽一个实例，允许实例重复；不是把三个实例强制一一分配。

认得阶段名称，还要知道它的含义

DRAFTING · 开局选牌CHOOSING_COLLECTION · 选藏品IN_PROGRESS · 可操作地图IN_BATTLE · 战斗中CHOOSING_REWARD · 战后选牌CHOOSING_UNEXPECTED · 事件选择UNEXPECTED_RESULT · 事件已提交VICTORY / DEFEAT · 终局

还有初始化用 SETUP。IN_PROGRESS 是“地图就绪”这一具体阶段，不是“整局未结束”的泛称。

当前默认配置

初始牌组为 3 打击 + 3 防御，再各选 1 张传说、史诗、稀有，合计 9 张。普通胜利后是一轮三选一，可跳过；Boss 胜利直接结算。脚本默认奖励轮数为 3，但 default_run.tres 覆盖为 1，要看有效资源而不是只看脚本默认值。

随机的可复现性：两个随机流，各管一类事

内容 RNG

决定地图绑定、Boss、候选等冒险内容。候选保存后重读，不因打开查看器、翻页或重试页面而重抽。

战斗 RNG

决定抽牌洗牌，与内容流分离；由初始种子异或常量派生。同配置、同种子、同行动序列可复现，尚没有完整的行动录制与回放系统。

BattleSession 才是规则入口，Controller 是适配器

Session 管“能不能”和“怎么算”

准备与激活、阶段合法性、费用与武器条件、有序效果、敌人回合、胜败、实际事件和最终结果。其状态对象包含玩家与敌人、能量、所有牌区、武器、状态与回合。

can_play_card 与真正的 play_card 共用检查入口。按钮置灰是提示，规则验证才是权威。

Controller 管“接到谁、交给谁”

连接 BattleView 的输入信号；创建并持有 BattleSession；把合法操作交进去；把实际事件和独立卡面快照交给表现；刷新视图后一次性向整局报告结果。

仍保留少量旧接口转发以兼容原有测试和调用。不能因此认为它仍然拥有第二套战斗规则。

一次出牌的同步规则顺序

  1. 检查：当前阶段、卡实例、能量、特殊前置条件

    必须是玩家回合、仍在手中的实际实例；不能正在结算或已经终局。

  2. 先构造效果队列，再提交费用与牌区移动

    ActionQueue 是 Callable 的 FIFO 同步队列；不是动画时间轴，也不是后台线程。

  3. 按顺序执行每个效果，产生实际结果事件

    先加力量再伤害，与先伤害再加力量不同；多段伤害逐段读取当前状态。自损致死可中断剩余效果。

  4. 完成牌区归档，检查胜败，再通知外层

    普通牌进弃牌堆，消耗牌进消耗区，能力牌和武器按各自规则去向。双方同时死亡时，失败判断优先。

抽牌堆手牌resolving_card · 结算中弃牌堆消耗区已打出能力已装备武器

牌区验证使用实例身份检查，避免同一张实际卡同时出现在两个区域。武器每个玩家回合只有一次攻击机会，重新装备不刷新本回合机会。

这不是通用事务回滚系统

若队列在部分执行后发生错误，已支付的费用和已发生的效果会保留，resolving_card 留在结算中以阻止后续命令。不能把“有校验、有提交边界”讲成“任何异常都能自动恢复原状态”。

伤害只保留一个权威算法

AttackDamageResolver
攻击伤害 = max(0, floor((基础值 + 力量) × 虚弱系数 × 易伤系数))

攻击者虚弱：×0.75；目标易伤：×1.5；全部乘完再向下取整。之后由目标的格挡吸收，得到实际生命损失。治疗联动使用实际生命损失，而非原始伤害。

9格挡前伤害
5生命损失上界

假设目标剩余生命足够；实际扣血还受当前生命上限约束。此处是教学演算，不调用游戏运行时。

例：基础 6 + 力量 2，虚弱与易伤同时存在：floor(8 × 0.75 × 1.5) = 9；格挡 4，最多扣血 5。预览通常展示格挡前伤害，不是预测整条效果链后的最终血量。

回合也属于规则，而非动画回调

玩家回合开始

按能力条件清除旧格挡 → 恢复能量 → 重置禁抽与武器机会 → 回合计数 → 回合开始能力 / 藏品 → 起手固有安排或正常抽牌 → 开放玩家阶段。

结束回合与敌人行动

弃掉非保留手牌 → 敌人阶段 → 敌方清理旧格挡与开始效果 → 执行当前行动 → 状态结算、行动下标推进 → 新玩家回合。意图与执行读取同一 current_action。

跨战斗传递的是结算，不是旧战斗对象

下一场从 RunState 的牌组定义、实际生命和最大生命创建全新实例；格挡、临时力量、手牌、武器耐久等不通过旧 BattleState 跨场复用。藏品按定义在新场的对应时机重新施加。

依据：battle_session.gdbattle_state.gdaction_queue.gdattack_damage_resolver.gd
05

Data-driven content

配置表达内容，代码解释机制

“数据驱动”不等于任何玩法都不写代码。资源可以组合已有机制；新增机制仍然需要扩展定义、验证和规则实现，再由内容资源使用。

卡牌：有序效果，而非名称分支

CardDefinition 定义基础费用、类型、稀有度、固有 / 保留 / 消耗、原画和 effects。每个 CombatEffectDefinition 描述一种效果、目标、数值与次数；数组顺序就是语义顺序。

“攻击牌类型”与“伤害是否受攻击修正”是不同维度：技能也可以配置攻击伤害，但不一定触发攻击牌专属的回能统计。

文案中的 {damage_0} 对应 effects[0]。它只格式化显示，不决定实际伤害；修改说明文字不会改变规则。

敌人：定义、状态、行动模式

EnemyDefinition 保存静态属性与行动模式，EnemyState 保存生命、状态与当前行动下标。敌人按配置的行动循环推进；目前不是自适应策略 AI，更不是模型推理。

EncounterDefinition 组合敌人和本场规则，例如每回合能量、抽牌数、手牌上限。CharacterDefinition 组合玩家定义、初始牌组和奖励池。

不期而遇：选项资源 → 结果提案 → 会话提交

选项定义→执行器查询可用性 / 候选→evaluate 结果提案→会话接受并应用→结果页 / 继续地图

选项拥有稳定 ID、选择方式、生命费用、治疗 / 获牌 / 删牌等操作、筛选条件和结果模板。UnexpectedEncounterExecutor 不直接修改本局，RunState 在验证后同步支付费用与应用收益，再进入 UNEXPECTED_RESULT。视图不用按“营地 / 祭坛 / 泉”重写三套业务。

扩展边界要讲具体

复用现有操作的第四个不期而遇，可以主要新增 .tres 资源并加入池。若要“升级卡牌”“多阶段交易”，需要新规则机制；当前获牌选项验证也固定为 3 个候选，并非任意数量都已支持。

藏品不是牌，它的触发点分属不同规则域

BATTLE / ACTIVATE

赤铜獠牙

战斗激活时获得 1 力量。由 BattleSession 应用，不在地图页面偷偷加属性。

BATTLE / TURN START

守誓盾徽

前 3 个玩家回合各获得 3 格挡。计数和触发在单场战斗规则内。

RUN / RESULT COMMIT

06

Commit boundaries & recovery

把“重复点击”和“加载失败”当真问题

可靠性不是多写几个 if，而是明确身份、阶段和提交时机。这里最值得在面试中展开：规则已经成功，页面却失败时，如何避免重复发奖、重复回血或重抽候选。

三类身份，解决三个不同问题

PAGE SOURCE

还是当前页面吗？

PageRouter.is_current 检查来源页面身份与存活状态，并在提交中拒绝回调，阻止已退出页面继续操纵流程。

STEP TOKEN

还是这一步操作吗？

页面连接时绑定当前 step_token。命令成功递增 token，旧回调即使迟到也不能重复提交同一步。

BATTLE + NODE ID

还是这场战斗吗？

结果必须属于当前 battle_id / node_id，且未被处理。再校验生命范围与胜负一致性，拒绝错场或重复结果。

兼容入口允许 token = -1，表示跳过步骤匹配。因此准确说法是“生产页面绑定 token”，不是“所有任意调用天然幂等”。

页面切换分两段，战斗启动也分两段

PREPARE / 隐藏准备

先准备候选页面，保留旧页面

实例化 → 检查根为 Control 且脚本匹配 → 放入最终 page_container → 隐藏、禁用处理 → 初始化。失败就丢弃候选，旧页保持。

BattleSession.prepare 只构建 SETUP；不启动回合，不抽牌，也不消费洗牌随机流。

COMMIT / 正式启用

提交身份，再退出旧页面

先设置当前页与 generation 并关闭重入入口 → 停止、隐藏和移除旧页 → 显示新页 → 排队释放旧页。新页不重新挂载。

提交成功后才调用 BattleController.activate_battle，启动首回合和反馈。

为什么准备后不能先摘下再重新挂上？

移出场景树会触发 _exit_tree。BattleController 会在这里 dispose 会话；若为“切换”重挂新页，就可能把刚准备好的战斗提前销毁。直接在最终容器里隐藏准备，避免这类生命周期副作用。

具体失败：战斗胜利已提交，奖励页创建失败

  1. 规则先确定事实

    RunSession 接受 BattleResult，回写生命，记录已处理身份，应用普通胜利藏品治疗，保存 RewardState 与候选，进入 CHOOSING_REWARD。

  2. 展示失败，不反向撤销事实

    Flow 展示导航错误浮层，提供重试或返回；状态仍是奖励选择。旧画面可能保留，但旧步骤回调不能再次生效。

  3. 重试只重新展示当前状态

    读取现有候选和生命，不重复提交 BattleResult，不再次治疗，也不重抽卡牌。返回菜单成功时结束当前局。

奖励和事件：候选先保存，确认才消耗

  • RewardState：保存所属节点、战斗、总轮数、当前轮、候选和提交记录；只有进入下一轮才抽样。当前配置是一轮。
  • 跳过：同样消耗当前奖励轮次，最后一轮完成后结束该普通战斗节点；不是一个只关窗口的 UI 行为。
  • 事件确认：验证选择属于既存候选、费用可付、删除索引有效，再在同步路径应用。关闭选牌子页不等于已经支付。
依据：page_router.gdgame_flow_controller.gdreward_state.gdrun_session_test.gd

动画和音效消费已经发生的结算。先确保“扣了多少血、哪一方受击”可靠，再决定飘字、闪光与声音怎样表达，而不是在动画结束时才扣血。

记录战斗 ID、事件顺序、来源、目标、类型与实际数值。例如格挡吸收后只损失 2 生命，就发出对应实际结果。

四个有理由的取舍

① 选同步规则，不让动画主导时序

回合制、单敌人场景下，同步结算更容易验证和复现。代价是复杂“中途选择”“连锁响应”不能靠随便加一个 await 解决，需要暂停/恢复命令协议或更明确的阶段机。

② 用 Resource，而非提前做通用编辑平台

复用 Godot Inspector 和资源序列化，内容与美术易接入。代价是资源类型、枚举编号和引用要保持兼容，模型仍依赖 Godot。

③ 页面按需创建，服务常驻

减少页面间隐式引用，退出后局部对象容易释放。代价是需要候选快照、当前状态恢复和明确的 prepare / commit；不能靠页面节点本身存整局事实。

④ 继续兼容已有入口

Controller 的旧方法转发和旧地图 REST 规则保留回归路径。代价是代码边界暂时不够纯；后续应迁移调用者、补同等证据后再删除，而不是直接改坏旧实验。

你最值得主动展开的一个难点

“普通战斗胜利后，规则已经提交，但奖励页可能加载失败。如果重试时重新执行胜利处理，就会重复回血或重抽候选。我的处理思路是把业务提交与页面展示分开：RunSession 先校验战斗身份，记录结果并固定 RewardState；PageRouter 隐藏准备页面，成功才切换。重试只根据当前状态重建页面，页面来源和 step_token 再阻止旧回调提交。这样，恢复操作不会变成第二次业务执行。”

练习时接着解释：为什么这不是数据库事务？为什么只禁用按钮不够？为什么 BattleSession 也需要 prepare / activate？你能回答这三个追问，这个案例才算掌握。

追问练习：先口答，再展开对照

分层为什么不把规则直接写在 BattleController？

控制器同时处理节点生命周期、输入和表现。如果费用、回合、伤害也写在里面，数值实验就必须实例化场景，界面修改也更容易碰到规则。抽出 RefCounted 的 BattleSession 后，Controller 只做输入和结果适配，游戏与实验调用同一套规则。

代价：多了显式上下文传递、事件桥接和对象生命周期管理。对于极小原型可以先简化，但本项目已出现奖励、不期而遇、数值实验与多页面恢复需求，边界有实际收益。

状态Session 和 State 有什么区别？RunState 是否纯数据？

Session 是生产命令门面：检查操作是否属于当前阶段与步骤，协调结果提交。State 保存事实，并提供基础状态转移与验证。当前 RunState 包含地图生成、节点和事件应用等较多逻辑，不是纯 DTO。

不要声称所有写入已经被语言权限完全封住；目前公开字段仍需收紧。拆分目标是更小的内聚模块与更明确的写入口，而不是把所有代码机械地搬进 Session。

资源为什么用 Resource？两张相同卡怎么保证互不影响？

Resource 适合 Inspector 编辑、类型化引用与 .tres 序列化。CardDefinition 共享静态配置，CardInstance 保存单张运行态；两张打击可以指向同一资源，但实例身份和临时费用不同。

Resource 只读主要靠契约，不是引擎自动冻结。必须避免把减费或武器耐久写回共享定义，否则所有引用者甚至下一局都会受影响。

身份为什么防重复要页面来源、token 和 battle_id 三种检查？

页面来源解决旧页回调；step_token 解决旧业务步骤；battle_id / node_id 解决结果归属与重复结算。三个检查覆盖不同身份，不能互相替代。按钮禁用只能减少 UI 重入，不能约束排队回调或其他调用者。

生产页面绑定 token；兼容的 -1 调用可绕过步骤检查。对结果另有 processed_battle_results 与阶段校验，不能简单承诺任意命令都天然幂等。

切页prepare / commit 和 prepare / activate 分别保护什么？

Router 的 prepare / commit 保护页面可用性和场景生命周期：旧页不提前删，新页在最终容器内准备。BattleSession 的 prepare / activate 保护业务时机：未提交的隐藏战斗不能先抽牌、推进回合或播反馈。

若新页准备后又移出再重挂，会触发 _exit_tree，可能 dispose 刚准备好的会话；所以 commit 不 reparent 新页。

队列ActionQueue 是异步动画队列吗？能撤销吗？

不是。它是 Callable 的同步 FIFO 规则队列，保证多个效果按定义顺序执行。动画消费实际结果，不驱动规则队列。

当前没有通用撤销：中途失败保留已发生费用和效果，结算中标记阻止继续命令。若未来支持反应卡或中途选择，应设计可暂停恢复的规则协议，不能直接在同步模型中混入动画 await。

事件有 BattleEvent，是否就是事件溯源架构？

不是。当前状态是权威，BattleEvent 传出实际反馈数值，服务于表现与音效。事件并没有承诺完整记录所有状态改变，也没有事件重放恢复状态的协议。

真正回放还需配置版本、初始状态、命令序列和随机状态。给事件带 sequence 有助于反馈排序和识别，不等于已有事件存储系统。

数值伤害预览如何避免和实际规则不一致？

统一 AttackDamageResolver，预览在局部模拟前序效果对力量、格挡、易伤等的影响，不修改实际状态。实际多段效果逐段使用当前状态，乘法完成后再取整，目标再扣格挡。

预览一般是格挡前伤害，不代表完整预测目标最终生命、后续触发与致死中断。治疗联动使用实际 HP 损失，不能拿预览数字当实际扣血。

随机只保存 seed，就能完整复现一局吗？

需要相同配置、版本和相同操作序列，并保持相同随机消费顺序。项目把冒险内容与战斗洗牌分成两个 RNG 流，并把已生成候选保存，减少 UI 行为对随机的干扰。

只有 seed 还不够做中途存档或完整回放；中途恢复通常还需 RNG 当前状态、阶段、候选和战斗实例状态等。当前没有持久存档。

生命周期为什么手牌动画要复制卡面，不能直接移动原节点？

规则执行后卡已离手，HandView 应立即维护真实手牌控件；若动画仍持有原节点，清理和切页会互相牵制。独立 CardFace 快照只持有表现数据与坐标，原控件可以正确释放。

这属于让表现脱离业务对象寿命。终局短提示还可交应用层浮层跨页完成，而普通战斗反馈随页面清理。

扩展新增卡牌、不期而遇、多敌人，各改哪里？

复用已有卡牌效果：新增 .tres 并接入角色池；复用已有事件操作：新增选项 / 事件资源并接入 RunDefinition。新增机制则要同时补定义验证、规则、显示与测试。

多敌人不是只复制 EnemyView：需要目标选择命令、稳定目标 ID、战斗状态的实体集合、效果目标解析和胜败判断等。当前单敌人的边界要先承认，再说明演进路径。

验证怎样证明重构没把游戏规则改坏？

在规则层检查费用、牌区、效果顺序、回合和结果；在流程层检查过期命令、候选稳定和结果单次提交；在生命周期层检查 Router、手牌和浮层；再做真实渲染与独立构建启动。

数值实验与游戏共用 BattleSession，降低双实现漂移。旧实验有固定配置条件，要原样保留并说明适用范围，不能用当前 UI 跑通代替历史数值契约。

取舍为什么不用 ECS、完整 DDD 或全局事件总线？

这个项目主要复杂度是回合规则、流程提交和页面寿命，不是大量实体同构计算。用类型化对象、显式会话入口和少量结果信号就能解决，额外框架成本目前没有对应收益。

也不是完全没有依赖注入：应用装配后传入音频和浮层等服务，但 Flow 仍会按场景路径找兄弟节点，部分旧调用保留兼容查找，不能说已全面容器化。

演进如果下一个需求是存档，你会怎么做？

先定义存档边界：地图阶段存档还是战斗中也支持。做版本化快照，保存稳定内容 ID、牌组条目、HP、路线、阶段、候选、已处理结果及 RNG 状态；加载时校验、迁移并解析资源，不能直接序列化整个场景树。

若支持战斗中，还需实例 ID、牌区、状态与武器等快照，且只能在明确稳定提交点保存。这是后续设计，不是当前已有系统。

没有匹配的追问，试试“状态”“切页”或“随机”。

面试时最容易说过头的六句话

别这样说改成准确表达
“所有模型完全脱离 Godot。”规则不依赖场景树和 UI，仍使用 Godot 的 RefCounted / Resource / 类型。
“资源不可变，任何地方都不能改。”静态资源按只读契约使用，部分容器只读；仍需约束共享对象写入。
“有事件和 seed，所以支持回放。”有反馈事件与分离随机流；还没有完整的版本化命令记录与重放。
“所有错误都会回滚。”初始化和展示有准备边界；战斗中途规则错误没有通用回滚。
“新增任何玩法只要配表。”已有机制可配置组合，新机制需要规则和验证扩展。
“这套架构已经没有问题。”边界已明确，但 RunState 偏大、部分状态公开、兼容转发和 CI 仍可改进。
